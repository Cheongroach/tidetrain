## 最初想完成什么

用户希望通过一个真实训练 infra 项目，理解源码和系统问题。任务 3 聚焦闲置、会加入退出且通信受限的 GPU；另两组负责 H20 和 910B4 的其他训练工作，不能把那两组结果算进 TideTrain。

用户优先要求 Spot-UCE，并指出撮合需要小时级等待。申请量与实际下发量可能不同。[原始目标与资源选择](CONVERSATION_HISTORY.md)。

## 为什么从共享存储改为 HTTP

起初考虑 GPU 直接访问 HDFS／ByteNAS。用户先确认不支持 ByteNAS，再说明 GPU 只能访问镜像和模型目录。决定于是变成：CPU 读写持久存储，通过 HTTP 调用 GPU，GPU 只用本地盘。

改变的是上传、下载、持久化和恢复的负责方。[挂载限制的原对话](CONVERSATION_HISTORY.md)。

原文检索小标题：`6ad986f4792beb2e66566a5a`、`6ada01b8792beb2e66566b7f`。

## 为什么反复区分副本和参与者

两笔资源需求后来扩大为 8+8，用户明确不要求为了原两卡程序缩容。实验仍只选两个算法槽位；平台副本多不是 DDP world size 多。有效 token 只随接受 commit 增长，失败尝试与独立重放不重复计数。

用户允许最多 1000 GPU／20,000 GPU·h 作为参考并容许超额，额度不是交付，也不能当作实际消耗。[扩大资源的原对话](CONVERSATION_HISTORY.md)。

原文检索小标题：`6adcf04e792beb2e66583074`、`6adcf09a792beb2e665830f9`。

## 真实实验回答了什么

四轮接受 524,288 token，21 个状态对象审计通过，一轮独立 A10 重放一致。完整验证 perplexity 却上升 32.87%。这两种证据分别回答恢复正确性和模型质量，不能合成“训练收益”。[终验汇报的原对话](CONVERSATION_HISTORY.md)。

## 千卡阶段发生了什么偏差

后续用户要求直接上千卡，不需要八卡爬坡，还要求排队按一周预留。实现增加分片、持久账本、就绪集合和独立计时，并做 CPU 控制面测试。
