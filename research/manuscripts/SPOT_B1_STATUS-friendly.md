# 第二轮 Spot 预约：申请、撮合、交付和训练是四件事

这份历史记录最重要的区别是：预约上填写多少卡，不等于实际下发多少卡，更不等于多少卡参加了训练。最初两笔各一张 A10，之后改成各八张，最终为 8×A10 和 8×A100 PCIe 80GB，合计 16 张资源需求。

## 一张卡的旧窗口实际发生过撮合

旧守护曾在 19:33 观察到两份各一实例的 A10 deployment，随后按当时 19:34 截止提交删除。LF 撮合距离申请约 47 分钟，另一侧被观察到交付约 56 分钟。此前没有即时下发，不能解释为始终没有撮合。

后端记录随后缩减，最终交付为零；删除提交和撮合记录都没有证明 CUDA 训练。这里的等待经验解释了为什么用户后来要求延后数日乃至一周。

## 两笔八卡预约怎样理解

当时订单最终回读为 8 张 A10、8 张 A100 PCIe 80GB，到 2026-10-26 20:00，北京时间。候选机房为 HL、LF、YG、ZJG、GL，`hl`／`lf` 只是逻辑槽位。库存、优先级或 Running 订单状态都不是确定交付时间。

后台每 300 秒通过官方服务／deployment 查询，必须匹配具体预约身份，避免操作无关部署。旧 19:34 清理期限已停止使用；新的到期记录与旧记录不能混为一份合约。

原程序每逻辑槽位只选择一个 GPU 实例，后来四轮实验实际为两卡。它没有实现两组八卡 DDP，所以不能把 16 个目标副本写成 16 卡训练规模。

## 哪种截止时间控制哪件事

预约有效期决定平台是否还应保留资源，CMD／worker timeout 限制一个进程寿命，控制 run 的 deadline 限制一个实验。进程退出不会自动取消预约；恢复控制器也不能延长不可变父 run。

早期的三小时限制是当时有限窗口，后来用户明确允许更长等待和更大资源。现已暂停操作，不根据本页旧的“下一步”重新申请。
