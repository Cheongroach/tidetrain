# GPU 执行记录：哪些失败影响了结果

这份历史进度表包含多次中断、镜像更换和状态更新。易读版先给终验答案，再按故障类型解释原因，避免读到早期“尚无成功更新”时误以为整个实验都未完成。

## 最后完成到哪里

Qwen2.5-0.5B 的两个单 GPU 槽位完成四轮，接受量 524,288 token；另一 A10 实例重放下一轮，delta、Adam、随机状态和游标一致。21 个远端提交对象、四轮参数和外层动量检查通过。完整验证 perplexity 上升 32.87%，因此恢复正确和模型质量退化同时成立。[终验报告](../../results/qwen05b-4round/REPORT-friendly.md)。

C1／C2／C3 是先后启动的控制会话，即同一实验在暂停或恢复时的不同控制器运行段。C3 接着 C1 的首轮已提交状态继续，C2 未提交的结果没有计入接受量。它们不是三个独立随机种子的质量实验。

## 失败怎样影响接受量

| 观察到的故障 | 对训练意味着什么 | 做过的修改及证据范围 |
| --- | --- | --- |
| job 仍显示 succeeded，临时 delta／recovery 已不见 | 算完不代表能持久化，不能计入全局接受量 | 改为先把两份产物都取到 CPU，再发布；谁删除了真实 GPU 文件仍未确认 |
| CUDA 驱动和用户态库不匹配 | 看见显卡名称不代表 BF16 运算能用 | 按实际探针选库；A10、A100 曾通过 BF16，不能推广到任意节点 |
| Transformers 导入失败或运行文件不见 | HTTP 服务存活也不能继续训练 | v9 改运行目录并检查依赖、模型配置、数据清单；清理主体未确认 |
| A100 端点变更或不可达 | 旧 IP 的身份不能继续代表原实例 | 重新发现并推进 generation，旧结果不再接受 |
| 约 4 GB 对象读取超过 300 秒 | 控制会话可能停在恢复阶段 | 大对象最长 900 秒且受剩余 deadline 限制；不能用延长单次超时改写不可变 run |

这些修改没有逐一确认所有真实故障根因。已执行的故障注入可证明协议处理方式；真实平台上的删除、端点变化或 SIGSEGV 若证据不足，仍按原因未确认保留。

## 怎样避免把未提交训练算进去

GPU 训练、HTTP 下载、HDFS 发布和全局提交是不同阶段。先绑定本轮基线和实例身份，完整收齐 delta／Adam／RNG／cursor，再校验并发布 update；最后全局轮次才能推进。上传了一半、旧实例结果或孤儿对象都不应推进游标。

首轮提交后曾停止唯一控制器，以空缓存从 HDFS 恢复，两个 GPU 实例也不同于首轮。独立重放比较已有产物，没有额外把它算进有效训练 token。

## 时间和内存为何看上去很不一样

GPU 每槽位每轮 128 步只需约 22–34 秒；控制器仍要装载、上传、回收、保存和检查 GiB 级文件。C3 会话耗时 4,401.539 秒，包含恢复和存储，新增 393,216 token，89.336 token/s 不等于单纯计算速度。

控制器 HWM 11.683 GiB，完整审计 HWM 15.904 GiB；串行执行在 32 GiB 环境中完成。全开发机 cgroup 还有其他进程和文件缓存，不能当作控制器自己的 RSS。
