# 扩展执行：千卡需求、CPU 测试与真实训练的区别

扩展阶段没有完成千卡训练。执行中选错了资源入口：创建的是 Merlin／Arnold Job 的资源需求，没有在用户要求的 Spot-UCE 预约入口取得千卡资源。用户后来停止这次尝试。原文中的排队状态和后台进程信息仅描述记录时刻。

## 1000 卡究竟怎样被写进请求

请求中的 `num` 表示实例数、`gpu` 表示每实例卡数。配置为 `worker.num=250`、`worker.gpu=4`，即 250 个实例、每实例 4 张 A10，共 1000 卡需求。此前也提交过 125×8 H20 和 13×8 H20 请求。预检成功、平台保留配置或创建 Pod 记录，只说明需求进入流程。

实际分配要看宿主机和 GPU 是否存在；实际参与训练还要看 CUDA 工作、worker 身份、提交记录和产物。这几层没有互相替代关系。

| 做过的事 | 实际观察 | 不能据此声称 |
| --- | --- | --- |
| H20 104／1000 卡需求 | 启动阶段失败；最近千卡修正版有 125 个无宿主机 Pod，退出码 -80003，具体根因未确认 | 已运行百卡或千卡 |
| A10 显式抢占配置 | 平台返回 `uce spot cluster cannot set preemtable`，之后移除此标志 | 移除标志就取得资源 |
| A10 短期限尝试 | 累计 11 个 trial；网关仍是 round 0、接受 token 0；停止后曾自动续试 | 成功训练或永久取消重试 |
| A10 一周期限需求 | 最后留存查询约提交两小时后仍 queued、无就绪 worker；随后用户停止尝试 | 一周等待已取得千卡 |

资源查询中过去出现过两队列 1426／1005 张 A10 余量，但 CPU／内存聚合余量为负。那是当前账号视角下的候选容量，不能等同于本任务交付，也不能直接解释未分配原因。

## 时间限制为什么重新设计

用户指出提交后通常至少 1–2 小时才有调度，要求按一周预留。代码因此把三种时钟分开：排队默认 604,800 秒；已分配节点等全员最多 21,600 秒；全部 1000 个有效租约参与者就绪后，才开始 2,700 秒训练窗口。总保护期限为 7 天 6 小时 45 分钟。

历史这次调度窗口到 2026-11-01 16:52:55，北京时间，总保护截止到当日 23:37:55。它是已停止请求的配置，不是当前新预约。

watcher 每五分钟读取状态，按有宿主机的分配时间累计保守 GPU·h，跨 trial 不清零，代码预算为 20,000 GPU·h（一张 GPU 分配一小时记为一 GPU·h）。缺失 stop 时间可能高估；这不是账单。本机网关和 watcher 曾独立运行，自动守护封装未通过验证并已移除，不具备已验证的进程自恢复或跨主机 HA。

## 目前代码已经验证了哪些部分

分片归约每次只处理少量 safetensors chunk。真实 Qwen checkpoint 的 CPU 检查覆盖 290 个存储 tensor、494,032,768 个参数、788 个输出 chunk；合成 delta 下结果逐 bit 与原 FP32 递推相同，误差为 0，峰值 RSS 1.61 GiB、耗时 359.906 秒。它测的是数学一致性和 CPU 内存，不是模型训练。[原始审计数据](qwen-shard-audit.json)。

15 项相关回归验证了过期／旧 fence 的 readiness、全员集合一次启动、CPU HTTP 两轮恢复、等待两小时不误停及跨 trial 成本累积。新 GPU 入口还没有完成全模型训练与质量验收。

## 1000 个逻辑客户端测试能说明什么

localhost 指同一台机器内部的本地网络。该测试由一台 CPU 主机产生 1000 个逻辑身份，客户端最多 64 并发，服务端最多 16 个请求槽。它处理两轮、每轮 1000 份合成更新，合成计数共 16,000 token；真实训练 token 为 0。

| 指标 | 结果 |
| --- | ---: |
| 总墙钟时间 | 69.237 秒 |
| 租约与就绪阶段 | 2.355 秒 |
| 两轮提交阶段 | 22.048／23.887 秒 |
| 两轮归约 | 5.635／5.596 秒 |
| 逻辑操作 P95 | 2.042 秒 |
| 网关 RSS／HWM 峰值 | 1,289,039,872／1,329,868,800 bytes |
| 网关线程峰值 | 18 |
| 最大提交记录 | 47,294 bytes |

重复请求没有重计，提交后的旧版本返回 409，第二轮恢复只返回当前 worker 的状态，集合只启动一次。delta 与恢复对象为共享合成数据，blob 准备时去重上传，因此不能用 69.237 秒推算千节点全量网络吞吐。[测试数据](control-plane-1000/report.json)。

## 尚未回答的问题

资源入口确认与真实千卡交付、多区域聚合、跨主机控制器接管、真实网络背压、固定 token 的质量对照仍未完成。当前只有一个 CPU HTTP 网关和单宿主机 SQLite；worker 仍完整恢复模型／optimizer 到 CPU。分片约束归约内存，没有减少总检查点字节。

继续实施前，应先确认正确资源预约路径，再以实际 GPU 列表、接受 token、完整产物和成本收齐作为验收。方法选择见[扩展设计](../../docs/SCALE_PLAN-friendly.md)，质量基线见[两卡实验](../../results/qwen05b-4round/REPORT-friendly.md)。
