# 两卡实验：恢复正确，但模型质量变差

这个实验同时问了两个问题：GPU 实例被替换后，能否继续原训练？继续训练后的全局模型，是否在相同验证集上变好？恢复检查通过；质量检查显示变差。两项结果需要分别理解。

## 训练了什么

模型是 Qwen2.5-0.5B，0.5B 表示约五亿参数，实际参数量 494,032,768。两个训练槽位分别使用 A10 和 A100 PCIe 80GB；每个槽位每轮训练 128 步，每步两条长度为 256 的序列，共四轮。

接受训练量的计算为：

$$
2\text{ 个槽位}\times4\text{ 轮}\times128\text{ 步}\times2\text{ 条序列}\times256\text{ token}=524,288\text{ token}.
$$

这里的“接受”指更新已进入持久化全局版本。算完但上传失败、过期或没有被提交的结果，不计入此数。8+8 是平台保留的副本数，算法参与者仍为两块 GPU。

参数和 Adam 状态用 FP32（32 位浮点数）保存，训练计算使用 BF16 autocast（部分运算自动使用 16 位浮点数）。每个槽位先本地训练，再由唯一 CPU 控制器执行外层 Nesterov 更新；这不是每一步都同步梯度的 DDP。

## 验证集上的变化

![训练前后的完整验证结果](../../docs/friendly/validation-quality-friendly.png)

两次评测均在 A10 上使用 FP32、batch=4、序列长度 256。相同验证流有 262,210 个 token，实际预测 262,209 个目标 token，覆盖 1,025 个窗口：1,024×256+65=262,209，最后 65 个目标 token 也计入。第一个 token 只提供上下文，所以目标数比数据流总数少一。

| 全局模型 | 完整 validation loss | Perplexity | 评测时间 |
| --- | ---: | ---: | ---: |
| 初始版本，round 0 | 3.087654460 | 21.925590258 | 29.610 秒 |
| 四轮后，round 4 | 3.371856719 | 29.132567861 | 31.492 秒 |

Loss 是每个目标 token 的平均负对数概率，perplexity 等于 exp(loss)；两者都越低越好。loss 增加 0.284202259，perplexity 相对增加 32.870%。此处只有一个训练实验，不能据此建立统计显著性、DDP 非劣性，也不能断言所有 local-SGD 配置都会失败。

worker 日志里的 local validation loss 只看本地模型的一个固定 batch，不能替代这份全局完整验证。

## 恢复检查具体证明了什么

每轮保留全局模型、外层动量，以及每个槽位的 Adam、随机数状态和数据游标。数据游标依次为 256、512、768、1024，Adam step 依次为 128、256、384、512。

独立 A10 实例从首轮已提交状态出发重放下一轮，完整 delta、Adam、CPU／CUDA／Python 随机状态、游标逐项一致，delta 最大误差为 0。四轮外层参数与动量递推检查也为 0；21 个唯一提交对象共 67,191,974,291 bytes，远端 SHA256 核验通过。

这证明了被检查那一轮的恢复确定性和四轮提交链路的完整性。没有运行“四轮全部不中断”的 GPU 对照，不能把结果扩大成任意故障下整条轨迹都已与不中断训练比较。

C3 继承 C1 已提交的首轮；C2 未提交的结果没有计入接受量。恢复过程中没有修改父 run 的配置身份或截止时间。

## 时间与成本的分母不同

| 口径 | 数值 | 包含什么 |
| --- | ---: | --- |
| 初始版本发布到最终提交 | 43,204.062 秒；12.135 token/s | 包含停机、镜像更新、恢复、失败、存储与空闲；不含最初资产准备和最终评测 |
| C3 控制器启动到最终提交 | 4,401.539 秒；89.336 token/s | 新增 393,216 token；含恢复、重试和持久化，排除 C1／C2 之间停机 |
| 已接受 GPU 训练循环 | 合计 224.427 秒，即 0.062341 GPU·h | 只含被接受的训练循环，不含加载、传输或空闲副本 |
| 平台副本采样积分 | 203.622 GPU·h | 184 个样本；含预热、失败和闲置，不是账单 |

203.622 GPU·h 排除了计数查询失败的 22 段区间，未知覆盖 5.131 slot·h；没有把未知当成零，也没有外推最后样本之后的消耗。由这份采样归一化得到 388.379 GPU·h／百万接受 token，只解释本次运行，不代表稳定训练效率。

C3 控制器 HWM 为 11.683 GiB；完整状态审计 HWM 为 15.904 GiB。HWM 是进程存活期间记录到的最高驻留内存，不等于整台开发机的 cgroup 总内存。这些工作在 32 GiB 环境中串行完成，没有因本次审计申请 Spark 或新开发机。

## 网络字节不能从对象大小直接推出来

提交存储里 67.192 GB 是唯一对象总大小；86.955 GB 是按接受任务序列化对象推算的 HTTP 预算。缓存命中、重试、报头和 TCP 开销会让实际网络流量不同，因此两者都不能称为物理链路测量。

成功任务曾仍显示 succeeded，但临时产物已不见；也观察到 import 失败、端点变化及大对象读取超过旧 300 秒超时。针对这些风险做了收齐产物再持久化、运行目录检查和大对象最长 900 秒读取等修改；部分清理与端点变化的根因仍未确认。

## 这次实验回答了什么

该实验完成了两卡训练状态提交、完整验证及一轮独立恢复重放，模型质量在所用设置下退化。27 项既有 CPU 回归干净退出；补充尾窗回归虽断言通过，包装器因沙箱限制返回 1，应分别记录。完整 GPU 评测与全状态审计命令返回 0。
