# 百卡／千卡扩展的判断

当前可验证的实现是两个单 GPU slot 的同步 local-SGD：128 步本地 AdamW 后提交 delta，外层 Nesterov 在唯一 CPU 控制器执行。Bernard 已交付的副本数不等于参与训练的 world size。两个真实 GPU slot 已完成四轮 commit（524,288 tokens），完整GPU评测、独立恢复重放和21份远端状态审计已完成。验证loss从3.08765446升至3.37185672、perplexity上升32.87%，没有证明质量收益。以下百卡／千卡内容仍是代码和字节契约推导，不能当成扩展实测。

## 已执行的控制协议规模检查

`scaling-control-probe.json` 使用本机 CPU、本地文件系统和 8 个参数的合成 tensor，执行 100／1000 个 logical worker 的两轮协议，分别用时 **0.687／6.248 秒**。缺席一个 worker 的 quorum 提交、重复提交不重复计数、迟到旧版本拒绝、空缓存控制器恢复、下一轮补入缺席者后的游标均通过。它没有启动 GPU、HTTP 多端点或 HDFS 压测，也没有覆盖跨主机双主，不能给出百卡吞吐。

按首轮真实 GPU update 字段展开，100／1000 个 worker 的 round manifest 分别为 **97,462／971,362 bytes**，仍在当前 HdfsStore 的 1 MiB 限制内；1000-worker 记录已有约93%占用，增加指标字段或重试明细前需要分片 manifest。原型已通过逻辑规模检查，真实数据平面的 TB 级传输仍需按下面的方案处理。

## 先消除中央数据路径

Qwen2.5-0.5B 有 P=494,032,768 参数，FP32 参数 D=4P=1,976,131,072 bytes（约 1.84 GiB）。当前 warm round 每个 island 下发参数 D 和前轮 optimizer 2D，回收 delta D 和 optimizer 2D，HTTP payload 至少 **6D≈11.86 GB/island/round**。冷首轮无需前轮 optimizer，为 4D。HDFS 每轮新增 delta/optimizer 3D/island，加全局参数和动量 2D。实际序列化略大，还需计入重试、校验、元数据和冷读取。

| GPU 数 | 每 island GPU | island 数 | warm round HTTP 下限 | 中央串行 10Gbps 理想时间 |
| --- | --- | --- | --- | --- |
| 100 | 1 | 100 | 1.186 TB | 949 s |
| 1000 | 1 | 1000 | 11.857 TB | 9485 s |
| 100 | 8 | 13 | 154 GB | 123 s |
| 1000 | 8 | 125 | 1.482 TB | 1186 s |

8 GPU/island 是后续设计，尚未实现。单中央端只是即使算力足够也会遇到的下限；不能靠并发 HTTP 将所有出口带宽放大。现有每次 HDFS CLI 调用还启动独立进程，首轮缓存修复后的恢复提交会话用时794.736秒，其中68次CLI命令耗时475.683秒；部分结果下载命中既有缓存，因此这个会话不是完整round通信基线。正结果缓存已减少重复读，但不是千节点元数据服务。

目标结构应是：**全局版本／成员控制器 → 区域分片聚合器 → 小型 island → GPU**。中央控制器只处理小 manifest 和版本提交；delta 分片在区域聚合器做流式加权归约，模型通过区域缓存扇出。GPU 仍只访问镜像、本地盘和受控 HTTP，区域 CPU 接入 HDFS。

## 开发机与 Spark 的边界

2026-10-25 C3四轮在当前32GiB限制下完成，5秒采样的控制器RSS峰值11.180GiB、HWM11.683GiB；完整状态审计在控制器退出后串行完成，HWM15.904GiB。本次没有迁移或申请Spark／新开发机。cgroup总占用还包含其他任务和可回收文件缓存，不能直接作为控制器常驻内存需求。完整状态审计、重放比较和最终评测已串行执行，避免多个4GB模型／optimizer状态同时存活。

用户允许在默认开发机不足时使用Dorado Spark，或申请新的8C32G开发机。新开发机相同容量不能解决算法峰值超出32GiB的问题，但可隔离其他进程。Spark适合有界、幂等的分片校验／归约；唯一状态控制器必须保持在单一driver或独立进程，不能由独立重试或推测执行的task重复发起GPU训练／提交版本。迁移先确认旧控制器退出，再从不可变commit恢复；leader fencing未实现前不做跨主机双主切换。

扩到百卡前，应让分片聚合器只保留当前tensor分片，并限制同时下载字节。扩大CPU数量可以提高独立校验或分片归约吞吐，不能消除中央出口、HDFS大对象发布或每轮完整optimizer传输的下限。[C3最终报告](GPU_REPORT.md)分别保留进程RSS/HWM、cgroup匿名内存／文件缓存、GPU计算、HTTP及HDFS阶段时间，以据此决定是否迁移。

## island 与容错

同机或同一可靠网络域内的 4–8 GPU 先用 DDP/FSDP 做本地训练，跨 island 才采用低频参数同步。不具备可靠组网的 Spot 单卡保持独立 island，不将跨地域 CPU/TCP local-SGD 说成原生 NCCL all-reduce。

每个全局 round 固定成员 epoch、分片计划和 token 预算，按实际接受 token 加权；不能把同一 logical worker 的多个平台副本重复计入。租约和 generation 应由持久化调度层 fencing。quorum 与超时绑定到 round；缺席者游标不推进，下一 round 的成员变更显式提交。千卡固定全员 barrier 对长尾／抢占敏感，应测量 quorum 下的质量和数据覆盖变化。

optimizer 应在同一区域 CPU 的持久存储保存，并在岛内复用，避免每轮全量回传中央再下发。但 optimizer checkpoint 频率 K 与全局 round 提交必须约定一致：K>1 会改变准确恢复语义，不能只改传输频率却仍宣称零重复计算。初版应 K=1、区域持久化；压缩 delta、误差反馈、增量 optimizer 再作为独立正确性和质量试验。

失效域：单 GPU、island、区域聚合器、唯一控制器分别测试。控制器需要带 fencing token 的持久 leader lease/CAS；本地 flock 不覆盖跨主机双主。数据平面连接并发、待聚合字节、下载队列、CPU/RAM、存储写入均有明确背压上限；重试用退避及总预算，不能让故障区域的负载涌向余下资源。

## 扩容是否值得

设 H 为本地步数，t 为步耗时，C 为通信＋提交耗时；有效比例近似 Ht/(Ht+C)。要达到80%，需要 Ht≥4C。必须测真实 C 和 H 的质量退化，不能只增大 H 获得表面吞吐。对于异构卡，优先同型组成 island，跨 island 用相同 token 预算；若快卡做更多步，必须明确这是另一个算法配置。

扩容顺序：2 个 slot 完成 GPU正确性／完整恢复 → 8–16 个真实训练 slot 的固定 token 对照 → 100 GPU 等价控制面压力和失败注入 → 有足够语料及稳定质量时申请百卡实测 → 分层数据路径通过后再做千卡。CPU 模拟的千节点测试只验证调度／提交，不提供 GPU吞吐或收敛结论。

当前 WikiText-2 训练流只有2,517,232 tokens。1000 个单卡 island 单 round 会训练65,536,000 tokens，数据会大量重复；因此千卡质量试验必须扩大固定版语料和独立验证集，而不是继续复用这个 smoke 数据。
